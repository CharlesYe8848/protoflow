# 上线公告模板

`docs/<docId>/doc.md` 的起始骨架。面向业务/客户，简洁专业，避免技术实现细节。
上线公告的上下文通常来自一份 PRD——`create_doc(kind:"release-note", from:"<prd-docId>")` 会把出处
记进 `doc.json.origin`，之后上游 PRD 出新版本时 `chain_status` 会提示回看。

第一行标题格式：`# 【模块】核心功能点概述上线`——让人一眼知道上线了什么，突出最核心的功能。
不用写 `<!-- protoflow:changelog -->` 标记——上线公告面向业务/客户，不展示"版本｜修改日期｜
修改人｜修改内容"这张内部协作用的修改记录表；这个标记本身是通用机制（写了就在原地渲染成表，
不写就没有），只是这份写作规范不需要它。版本历史仍然完整保留在 `doc.json`/`versions/` 里，
只是不在正文展示——PRD 这类内部协作文档会写这个标记，所以保留展示。

---

```markdown
# 【模块】上线主要功能点概述：如"支持XX能力、YY功能、ZZ优化"

# 一、功能概述

[简述功能背景 + 核心价值，2-3 句话。多个功能上线时，优先突出最核心的，其他小优化在这里一句带过]

# 二、上线内容

- **[功能点1]**：[一句话说明能力 + 关键限制/细节]
- **[功能点2]**：[……]

[精简原则：相关联的功能点合并整合，避免碎片化。同一功能的多个子功能（配置/发起/审批/列表管理）
合并到一个功能点下]

# 三、解决场景

1. **[场景名称]**：[问题描述 + 如何被解决]
2. **[场景名称]**：[问题描述 + 如何被解决]

[数量与上线内容的核心功能点一一对应；多个相关问题合并到一个场景下]

# 四、功能介绍

**步骤说明**

💡 **Tips**：

- **[限制条件]**：[描述]
- **[注意事项]**：[容易出错的操作提示]

[Tips 精简原则：不是每个功能都必须有。去掉常识性权限说明、界面展示细节、建议性内容；
保留重要的限制条件、易错点、新功能的核心变化说明、关键业务规则]
```
