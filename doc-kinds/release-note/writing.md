# 上线公告撰写规范（doc.md）

## 语言风格

- 简洁、专业、面向业务，避免技术实现细节（除非必要）。
- 每个功能点 = 一句话说清能力；先讲"问题"，再讲"功能"。
- 面向客户的文案润色：去技术术语感，用更自然的表达（"对结果有异议"代替"不认可结果"）；
  先讲核心用户角色能做什么；合并同类操作；"同时支持…"比"附带…两个优化项"自然。
- 保持核心信息完整，不遗漏关键功能。

## 标题命名规范

标题让人一眼知道上线了什么，突出核心功能：

- ✅ 【绩效】组织绩效支持结果申诉上线
- ✅ 【招聘】职位多渠道关联、邮箱自动匹配功能上线
- ❌ 【绩效】4月份优化上线公告（太模糊）
- ❌ 【招聘】功能上线（太笼统）
- ❌ 把三四个功能点全堆进标题（太冗余）

多个功能上线时，优先突出最核心的，其他小优化在「一、功能概述」里一句带过。

## 结构精简原则

- 上线内容：相关联的功能点合并整合，避免碎片化；同一功能的多个子功能（配置/发起/审批/列表）
  合并到一个功能点下。
- 解决场景：数量与上线内容的核心功能点一一对应；多个相关问题合并到一个场景下。
- Tips：不是每个功能都要有。去掉常识性权限说明、界面展示细节、建议性内容；保留重要限制条件、
  易错点、核心变化说明、关键业务规则。
- FAQ：至少 3 条，覆盖用户最关心的问题；Q 行末使用 `<br>` 硬换行，让 A 独立显示在下一行。

## 定版（finalize）

- 起草完 → `finalize(note:"首版")`
- `note` 一句话说清这次改了什么，记进版本历史（`doc.json`）——上线公告正文不放
  `<!-- protoflow:changelog -->` 标记，所以不展示修改记录表（面向业务/客户），但历史照样完整
  保留，`list_docs`/chain_status 用得到
- 已 `record_publish` 的版本冻结，之后改动进下一个版本
