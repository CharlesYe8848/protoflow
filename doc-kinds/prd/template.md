# PRD 模板

`docs/<docId>/doc.md` 的起始骨架。`create_doc` 会把下面这份填进 `doc.md`，把方括号提示替换成真实
内容。第一行 `# 标题` 会被当作这个文档在 `list_docs` / 画布菜单里的标题——**只写这篇 PRD 的主题
一句话**：不带项目名（项目上下文由所在项目提供）、不带「PRD」之类类型字样（画布菜单单独显示类型）、
不带版本号（版本另有整数序号，也单独展示）。例：`# 推荐候选人卡片与通用详情侧栏`，不要写成
`# 薪灵信息卡片样式优化 PRD —— 推荐候选人卡片与通用详情侧栏`。
`create_doc` 传了 `title` 时这行会自动填好，不用手改（目录名不受影响，还是 `docs/prd/`）。

目录层级（一~五）不要随意增减一级/二级标题，但每一章写多细按 writing.md 的「动态适配」规则调整。

`<!-- protoflow:changelog -->` 是修改记录表占位标记——**保留原样、不要手写表格行**。每次
`build_doc(mode:"finalize")` 定版时，系统按你给的 `note` 在标记原地自动重新生成这张四列表
（版本｜修改日期｜修改人｜修改内容），累积全部历史版本。删掉这个标记的话，这份 PRD 就不展示
这张表了——PRD 是要展示的，所以保留原样，不要删。

---

```markdown
# [这篇 PRD 的主题，一句话；不带项目名 / 不带「PRD」字样 / 不带版本号]

<!-- protoflow:changelog -->

# 一、项目概述

## 1.1、背景

[结合需求与现状精炼表述，最好带上行业/岗位等信息。只写现状、痛点、业务诉求，不要混入
"因此我们计划做 XXX"这类方案性表述——方案是三、四章节的事]

## 1.2、目标

[提炼 1 个核心目标即可，最多不超过 3 个；尽量数据化，从人效/客户价值等维度描述，
例如：人效由 10 分钟提升至 30 秒]

## 1.3、验收标准

[必填，用可量化、可衡量的数字化表达写出 1-3 条，明确怎样才算达成项目目标]

1. **[量化指标1]**：[例如：上线后 1 个月内，跨时区员工补卡报错率下降 90%]
2. **[量化指标2]**：[例如：管理员处理异常工单的平均处理时间由 15 分钟缩短至 0]

# 二、需求分析

## 2.1、用户故事

[格式：作为一名【角色】，期望通过【某种操作/功能】完成【某件事】，最终实现【某个价值/目标】]

## 2.2、需求清单

[数量必须跟用户提的原始需求数量 1:1 对应，不要把 1 个需求自己拆成/发散成 N 个子需求]

| 优先级 | 说明 | 备注 |
| :--- | :--- | :--- |
| P0/P1/P2/P3 | [需求简要说明] | [补充备注] |

# 三、产品方案

## 3.1、流程图

[能用 mermaid 画图就直接画（fenced code block，本地预览会渲染，不转图片）；
否则写清晰的文字流程描述，例如：员工张三发起审批 → 经过李四授权 → 流转至王五审批]

## 3.2、方案概述

- **[关键词1]**：[具体方案说明]
- **[关键词2]**：[具体方案说明]

# 四、需求详情

## 4.1、[需求名称1]

[可选：先放一张画板截图给出整体观感，再展开下面的详细规则]

![状态说明](assets/<captureId>.png)

### 1、产品逻辑

[无序列表，每条「**[关键词]**：说明」，关键词参考：基础说明/业务规则/校验条件/边界情况——
既要写正常流程，也要写负向流程的边界情况]

- **[基础说明]**：[具体说明]
- **[业务规则]**：[具体说明]
- **[校验条件]**：[具体说明]
- **[边界情况]**：[具体说明]

### 2、交互逻辑

[无序列表，每条「**[关键词]**：说明」，关键词参考：正常流程/异常流程——异常拦截要配清晰的
阻断交互 + Toast 文案；列表/数据加载要写空态兜底]

- **[正常流程]**：[具体说明]
- **[异常流程]**：[具体说明]

### 3、字段详情

[表格，内容靠左对齐。"规则"列按控件类型分维度换行：
【按钮/功能】写 1、显示说明 2、功能说明；
【下拉/单选/多选】写 1、默认选项 2、可选项 3、是否必填 4、功能说明；
【文本/日期等输入展示类】写 1、取值规则 2、格式]

| 序号 | 字段 | 控件 | 规则 |
| :--- | :--- | :--- | :--- |
| 1 | [示例按钮] | 按钮 | 1、显示说明：xxx<br>2、功能说明：xxx |

## 4.2、[需求名称2]

[需求多于一个时依次列出 4.2、4.3……，每个都按上面 4.1 的三段式（产品逻辑/交互逻辑/字段详情）写]

# 五、运营相关需求

[中大型需求必填；小型优化/Bug修复且确无数据埋点、历史数据兼容、权限变动时可整章省略]

## 5.1、数据埋点

| 事件名 | 事件描述 | 事件截图 | 埋点类别 | 埋点形式 | typeStatus和typeStatusKey | typeValue和typeValueKey |
| :--- | :--- | :--- | :--- | :--- | :--- | :--- |
| | | | | | | |

## 5.2、历史数据

[历史数据兼容方案或清洗迁移方案]

## 5.3、权限需求

[无明确复杂权限变动时写一段说明文字即可；涉及菜单/角色权限变动才需要下面两张表]

### 5.3.1、权限角色需求

| 序号 | 一级菜单 | 二级菜单 | 三级菜单/操作点 | 备注说明 |
| :--- | :--- | :--- | :--- | :--- |

### 5.3.2、权限矩阵说明

## 5.4、术语说明

[提取文档中出现的业务专业名词/系统专有概念/技术黑话，逐条解释]

| 序号 | 术语名称 | 释义/说明 |
```
