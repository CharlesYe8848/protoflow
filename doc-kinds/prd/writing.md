# PRD 撰写规范（doc.md）

- 心智：`doc.md` 就是这一文档的正文本身，手写 markdown，不是由结构化 JSON 驱动生成的——
  骨架照 template.md 填；目录层级（一~五）不要随意增减一级/二级标题，但每一章写多细按下面
  「动态适配」的规则调整。
- 修改记录表：正文里只放 `<!-- protoflow:changelog -->` 一个标记，**不要手写表格行**。每次
  `build_doc(mode:"finalize")` 按你传的 `note` 自动重新生成整表，累积全部历史版本。

## 动态适配（先判断需求体量，再决定写多细）

- 中大型需求/核心业务重构：一~五章节必须严格、完整地输出，产品逻辑和交互逻辑要做深度的结构化
  拆解。
- 小型优化/Bug 修复/轻量级插件：三、产品方案与四、需求详情可以适当简化，避免过度设计；确实
  没有数据埋点、历史数据兼容、权限变动等要求时，五、运营相关需求可以整章省略。

## 质量控制（写完对照检查一遍，这是测试侧的强诉求）

1. **边界问题明确**：正向操作、负向操作都要写清楚。所有异常拦截（字数超限、格式错误、网络
   异常）都要配套清晰的阻断交互 + Toast 提示文案；列表页/数据加载要明确空态兜底展示（暂无
   数据/显示短划线/隐藏整行）。
2. **逻辑严密闭环**：要考虑并发冲突与极端场景——比如员工正在用某功能时管理员突然停用/卸载
   了它，进行中的任务怎么处理、前端怎么阻断；多段雇佣/二次入职这类取值判定逻辑必须闭环，不
   能留缺口。
3. **消除不确定性**：不能出现"可能/也许/大概/视情况而定"这类模糊表述，每条规则和逻辑必须
   确定、可执行。
4. **条件穷举**：用"在 A 情况下是 X 结果、在 B 情况下是 Y 结果"这种分支写法穷举所有可能，
   绝不允许前后文案自相矛盾（比如前面说不支持、后面又说支持）。
5. **术语高度统一**：同一个概念全篇只用一个指定名词，绝不允许混用。
6. **复杂逻辑必须配案例**：业务规则复杂、晦涩或容易有歧义时，必须补一个具体例子——比如说
   "某列无值则忽略"，要用案例指明是保留历史数据还是清空为 null。
7. **B 端深水区排查**（推演产品逻辑/交互逻辑时主动想一遍，别等测试提出来才补）：
   - 数据更新规则：批量导入或编辑时遇空值，是保留历史数据还是覆盖清空。
   - 状态中断与容错：进行中的长任务/审批，若依赖的功能被突然停用/卸载，系统怎么拦截、报错
     或降级处理。
   - 复杂取值规则：涉及人员信息时，多段雇佣/二次入职/跨时区等场景的取值基准必须明确。
   - 冲突与空态：多前置条件或权限冲突时的优先级拦截规则；搜索无结果、列表无数据的空态兜底。
8. **背景绝对纯粹**：「一、项目概述」的「1.1、背景」严禁出现"因此我们计划开发 XXX""本需求
   将实现 XXX"这类方案性表述，必须 100% 客观陈述痛点、现状或业务诉求——方案是三、四章节的事。

## 开放问题（确实还没定的事，怎么标记）

写作过程中难免遇到真正悬而未决、需要与研发/干系人确认才能定的事（技术能力边界、异常兜底策略
等）——这跟上面「消除不确定性」禁止的"可能/大概"含糊措辞不是一回事：那条要求的是"能写清楚的
必须写清楚"，这里说的是"确实还没法在这一版里写清楚，但不能装作没这回事"。遇到这种情况，用
**加粗** 包住含"确认"或"待补充"字样的短语显式标出来，例如 `**需要与研发确认**`、
`**技术方案待确认**`。

`_shared/checks/open-questions.mjs` 会扫描这类标记。`build_doc(mode:"finalize")` 只是把它们
列进结果里（提前可见）；真正的拦截发生在 `record_publish`——任何 error 级 finding 都会挡住对外
发布。确需带着这些问题先发布（比如已口头对齐、只是没回填文档），调用时传
`acknowledgeFindings: true` 显式跳过。

## 需求颗粒度

「二、需求分析」的需求清单、「四、需求详情」的条目数量，必须跟用户提的原始需求数量 1:1 对应
——不要把 1 个需求自己拆成/发散成 N 个子需求，也不要过度发散。

## 表格

所有表格的分隔符统一用 `:---`（强制左对齐），不要用 `:-:`（居中）或裸 `---`（有些渲染器会
默认居中）。

## 呈现形式：按内容要传达的信息选，不按它怎么实现的

一块画板要放进 PRD 时，先判断它主要在传达什么，再选形式——不是"画板就等于截图"：

- **关系和逻辑**（流程、时序、层级、状态机、架构、依赖）→ Mermaid（` ```mermaid ` fenced
  code block，`preview.html` 会照常渲染成矢量图，带"图 / 源码"切换）。
- **界面和视觉**（布局、间距、配色、组件外观、真实产品截图）→ 图片。
- **混合内容 → 优先拆分**：能独立成篇的部分拆出去（图 → mermaid、表 → markdown 表、说明 /
  结论 → 正文）。但**排版本身是信息时不拆**——两套流程并排对比、颜色区分角色或风险等级、
  图与说明结论形成视觉分组、整体布局就是评审对象——这些整块截图或混合呈现。
- 以上都不适用、Mermaid 无法准确表达时，才截图。真正转不了的是少数：手绘批注、真实产品
  截图、配色本身编码信息且主题表达不出、精确间距 / 对齐是评审点的布局。

**Mermaid 从哪来**：

- 画板里有可直接使用的 Mermaid DSL → 优先复用。
- 没有、无法确定当前状态（如 `const flow = scheme === "a" ? flowA : flowB`）、DSL 是拼接 /
  函数生成、或画板根本不是 Mermaid 实现但表达了某种关系 → 按画板表达的关系生成等价 Mermaid。
- 图随状态变：关心哪些状态就各写一个 ```mermaid 块（方案一 / 方案二），不因为多态退回截图。

**跟 captures.json 的关系**：能由 Mermaid 完整表达主要信息的关系 / 逻辑类画板，**不进入
`captures.json`**（直接在 doc.md 写 ```mermaid 块）；存在 Mermaid 无法保留的重要视觉信息
（并排对比、颜色编码、图与说明的视觉分组、布局本身是评审对象）时，才截图或混合呈现。

## 截图流程（四步，跟 build_publish_pack 的 previews/capture/seal 是同一条流水线）

1. 写 `docs/<docId>/.build/captures.json`（声明这个文档要截哪些画板的哪些状态；格式见
   get_guide("capture")）→ `build_doc(mode:"snapshot")`：把 captures.json 引用到的画板源码/
   标注冻结进 `.build/snapshot/`，供接下来截图。**先按上面「呈现形式」筛一遍**——能走
   Mermaid 的别放进来。
2. `build_publish_pack(mode:"previews")` → `build_publish_pack(mode:"capture")`（无头浏览器
   自动截图，不弹窗口；actions 表达不了的复杂交互才退回浏览器工具手动截图）→
   `build_publish_pack(mode:"seal")`：核对后把截图落进 `docs/<docId>/assets/<captureId>.png`。
3. 写 `docs/<docId>/doc.md`——照 template.md 骨架填正文，「四、需求详情」涉及具体交互状态的
   地方用标准 markdown 图片语法引用：`![说明](assets/<captureId>.png)`。
4. `build_doc(mode:"finalize", note:"这一版改了什么")`：校验图片引用是否都已 seal、算指纹、
   冻结成 `versions/<n>/`、重渲染 `preview.html`、跑 checks。纯 prose 改动（画板/截图没变）
   可以直接 finalize，复用已有的 `.build/` 产物，不用重跑截图流水线。

## 何时定版（finalize）

- 起草完初稿 → `finalize(note:"首版")`
- 按一轮评审意见改完 → `finalize(note:"补充异常兜底与空态")`
- `note` 就是修改记录表「修改内容」列，一句话说清这次改了什么，别塞版本号
- 不想为某个小改动单独留版本 → 先不 finalize，攒到下次一起切
- 已 `record_publish` 的版本冻结，之后的改动进下一个版本

## 其它约定

- 图片引用规则只管 `assets/` 这一种来源——正文里额外贴外部图床/手画架构图用完整 URL，不受
  这条规则约束。
- 图片还是 Mermaid、什么进 `captures.json`，见上面「呈现形式」一节。
- 标题第一行（`# 标题`）只写这篇 PRD 的主题一句话：不带项目名（项目上下文由所在项目提供）、
  不带「PRD」之类类型字样、不带版本号（版本另有整数序号，画布菜单单独展示）。例：
  `# 推荐候选人卡片与通用详情侧栏`。`create_doc` 传 `title` 时这行会自动填好；目录名不受影响，
  还是 `docs/prd/`（同项目一种类型多篇时才显式传 docId）。
