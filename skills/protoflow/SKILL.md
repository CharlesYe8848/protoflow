# ProtoFlow

ProtoFlow 是一个框架加几个独立产品：**画布**（原型：页面、画板、标注）、**文档**（markdown）、
**表格**（数据 + 样式）、**绘图**（脑图、流程图等，文本写、自动排版）、**幻灯片**（每页一个 HTML，样式随意写，
可嵌表格、绘图）。产品可以按插件启用或禁用，当前有哪些用 `protoflow plugins` 看。产品之间只通过引用关联。把它们串成某种业务流程（比如原型 → PRD → 上线
公告）的模板、写作规范和脚本在**流程 skill** 里，不在工具里。

这份 skill 只做两件事：从项目状态开始，按交付物路由。工具怎么用见运行时的指南
（`get_guide`），这里不重复。

## 用 CLI

所有操作都走 `protoflow` 命令（没装全局命令时用 `node /实际仓库路径/bin/protoflow-cli.js`）：

```bash
protoflow --help                     # 每个工具一行
protoflow help <工具>                 # 完整说明和参数
protoflow get_guide --topic workflow  # 首次进入先读工作流
protoflow <工具> --参数 值 …            # 值是 JSON 就按 JSON 解析；写成 @文件 就读文件内容
```

- **定位项目**：用户正开着 ProtoFlow 的页面（浏览器标签页地址是 `http://127.0.0.1:<端口>/p/<项目>/…`）时，直接
  `protoflow get_project --url <这个地址>`，之后每个命令都可以用同一个 `--url`；不要去磁盘上找项目或读
  `~/.protoflow/projects.json`。没有页面时用 `--projectId <项目文件夹名> --dir <父目录>`，不确定就先 `list_projects`。
- **结构化信息只从命令拿**：项目结构、画布/文档/表格清单、版本、引用、健康检查都在 `get_project` 的返回里
  （`--findings true` 带上完整检查项）；不要读 ProtoFlow 的源码来推断怎么操作，没有的操作就说明做不了，不要
  自己改 `canvases/`、`docs/`、`sheets/`、`diagrams/` 下的元信息或 `rm` 目录（删除用 `delete`）。
- **正文直接改文件**：画板 `source.jsx`、标注、`doc.md`、`sheet.json`、绘图的 `pages/` 下的文件可以用文件工具读写（路径在 `get_project`
  里），改完用对应命令校验和定版。
- 指南里写成 `工具(参数:值)` 的地方，对应 `protoflow 工具 --参数 值`。

CLI 不可用、路径也未知时，说明缺少连接并询问安装位置，不能声称已经生成预览或完成构建。

## 1. 从项目状态开始

按第一条匹配的执行，不再往下看：

| 状态 | 做法 |
| --- | --- |
| 对已有项目的具体操作（预览、导出、检查、发布） | 只做这件事。`get_project` 找到对象，按 `workflow` 指南对应场景执行 |
| 对已有项目的具体修改 | 直接改，不重新访谈。修改原型走下面「修改已有项目的最低闭环」 |
| 已有项目、要继续某条流程（比如已有 PRD 要更新） | 看 `get_project` 的 `graph` 里产物的 `labels`，交给打这个标签的流程 skill |
| 新建 | 按下面第 2 节路由 |

项目恢复的具体步骤（`projectId`/`dir` 关系、`list_projects` 消歧、找不到时的处理）在 `workflow`
指南开头，按其执行。

## 2. 按交付物路由

匹配用户要的**交付物**，不是对话里顺带提到的词。用第一条匹配的：

| 优先级 | 交付物 | 去哪 |
| --- | --- | --- |
| 1 | 基于 ProtoFlow 原型的 PRD、上线公告，或检查它们是否落后于原型 | 流程 skill `protoflow-product-dev` |
| 2 | 供演示或评审的产品原型（用户不必提到工具名） | `workflow` 指南「新建原型」，画板能力见 `artboard` 指南 |
| 3 | 结构化数据表格（AI 写数据、人预览/导出 Excel） | `workflow` 指南「新建或更新表格」（`create_sheet` → `build_sheet`），字段见 `sheet-schema` 指南；不依赖原型 |
| 4 | 用户明确要用 ProtoFlow 写的独立文档 | `workflow` 指南「写或更新文档」 |
| 5 | 做原型之前梳理思路：需求拆解、流程、时序、状态（人看图提意见，你改） | `workflow` 指南「梳理思路」（`create_diagram` → `build_diagram`），写法见 `diagram` 指南 |
| 6 | 幻灯片（PPT）：汇报、评审、方案，也包括相册、纪念、活动、教学 | 流程 skill `protoflow-slides`（每页 HTML 自由写 + 检查） |

各流程 skill 的契约（输入 → 输出，什么时候选它）：

- **protoflow-slides**：输入是要讲的内容（可以引用项目里已有的表格、绘图，或照片、视频）；输出是按场合和内容设计、
  过了检查、定过版的幻灯片（能导出单个 HTML）。触发："做个 PPT""做汇报幻灯片""把这张表放进幻灯片""做个生日相册"。只要一张图、一篇文档
  时不选它。

- **protoflow-product-dev**：输入是项目里已定版（或即将定版）的原型；输出是带原型截图、引用原型版本
  的 PRD，以及基于 PRD 的上线公告，外加发布前检查和关系体检。触发："根据原型写 PRD""出上线公告"
  "PRD 跟原型对不上了吗"。只有 PRD、没有原型也没打算做原型时，不选它，按优先级 4 写独立文档。

读流程 skill：已安装就直接用；没安装就读 ProtoFlow 仓库 `skills/<名字>/SKILL.md`。不符合契约就继续往下
路由，不硬套。

### 不确定时

- "做个后台页面""写个 PRD"但没有原型交付或已有项目上下文：先结合代码库和对话判断；仍不明确时问
  一个关于交付物的问题，不因出现"页面"或"PRD"就创建项目。
- 明确指定 Figma、其他工具或生产应用代码：沿用指定工具。只有另外要求 ProtoFlow 交付或明确迁移时
  才进入；不假定外部设计文件可直接导入。

## 修改已有项目的最低闭环

- 修改前用 `get_project --findings true` 读取项目结构和现有问题，区分既有问题与本次影响；
  同时读取目标源码及已有标注，不凭预览图猜实现。
- 通过 `save_artboard_source` 保存源码并检查返回的 `idAudit`。元素、交互或语义变化影响
  已有标注时，实际核对后用 `write_annotations` 更新；纯视觉调整且语义不变时无需重写标注。
- 验证本次影响的交互链路：用户操作、状态变化和可见结果。源码检查不足以确认，或用户明确
  要求验收时，再使用浏览器实测。
- 修改后再次 `get_project --findings true`，解决本次改动造成的 broken/review 项，并报告引用了它的文档是否过期。
  只改原型时不自动更新文档；任务包含文档交付或同步时，交给对应的流程 skill。
- 改完一轮 `build_canvas(note:"这次改了什么")` 定一个新版本；没定版的改动不会出现在画布页上。

## 完成交付

按工作流完成标准收尾，给出所需预览、导出文件或检查结果。
原型默认按 `artboard` 指南做轻量检查；浏览器验收按需触发，不自动走完整业务路径。
如实区分源码检查与浏览器实测。本地预览链接只供本机访问。
文档或渠道落后时说明影响，按本次范围决定是否更新，不为消除提示擅自定版或发布。
